## 一、工具是什么？LLM 为什么需要工具？

工具就是函数，用来提供给模型感知外部环境的能力。

例子：用户问附近的商店在哪？模型并不知道你的地点和附近的商店。于是模型调用定位工具，然后通过模型告诉客户端我需要定位工具，于是客户端去调用定位工具，客户端获取到定位结果之后再把附近的商店结果告诉模型，模型整理之后告诉用户附近的商店在哪。

> ⚠️ 订正：例子里「于是模型调用定位工具」这半句是旧口误滑出来的，紧接着自己纠正成了「模型**告诉客户端**我需要定位工具、客户端去调用」——以后半句为准：模型只发调用请求，动手的永远是客户端程序。
>
> 💡 补充 1：工具补的是模型的两个洞——①「不知道」（训练截止后的事、此刻的实时状态；本例堵的就是这个洞）；②「不会算/做不了」（模型天生不擅长的活，如精确算术 → 计算器工具）。
>
> 💡 补充 2：「感知外部环境」只说了一半——工具既能**感知（查）**也能**行动（做）**：查天气/定位是读外部世界，发邮件/写文件是改外部世界。
>
> 💡 补充 3：这个例子实际可能要**两个工具、转两轮**：先调「定位」拿到位置（Observation 1），模型发现还不够，再调「附近商店搜索」（Observation 2）才收口——正好预演了「结果不够 → 再转一轮」的循环。

## 二、整条链（7 步，每步标注【模型】还是【我的程序】）

我的作答（隔时重测，原话）：

用户问巴黎今天多热，这句话被模型接收，然后模型会去检查自己有没有可以调用查询天气的工具，如果有，模型会查看工具的描述，根据工具的描述来生成对应的参数(Action)（停止生成）给工具去调用客户端去调用工具，然后工具接收完参数(解析)后，返回结果通过客户端返回给模型（Observation），如果结果是想要的，那么模型根据返回结果来输出内容给到用户。如果不是想要的模型会继续去调用工具来得到想要的结果。

> ⚠️ 订正（解析的位置）：原文把「(解析)」标在了「工具接收完参数」上——错。经追问后自己订正对了：**「解析的对象是 JSON（模型吐出的 Action），客户端解析，发生在调用工具之前」**——不然客户端根本不知道该调哪个函数、参数从哪来。记法：「停止并解析」横跨交接棒两端——**停 = 模型侧**（Action 吐完闭嘴），**解析 = 客户端侧**（读 JSON → 认函数 → 抽参数）。
>
> 💡 补充 1：「模型会去检查自己有没有工具」的精确说法：工具清单是客户端随请求塞给模型的（system prompt 或 `tools` 参数），模型是**看菜单点菜**，不是「翻自己口袋」。
>
> 💡 补充 2：「给工具去调用～客户端去调用工具」这句前半滑了一下、后半自己扶正——当天第二次同款自纠（第一节也有一次）：「动手的主语 = 客户端」在焊，但复习时还得盯这个点。

对照版（当天带读验收过的标准 7 步，复习用）：

```text
第 1 步：【我的程序】把用户问题 + 工具说明书一起发给模型
第 2 步：【模型】看说明书选中 get_weather，生成调用请求 JSON（= Action），吐完立刻停 ←「停」
第 3 步：【我的程序】解析 Action：认出调 get_weather、抽出 location=巴黎 ←「解析」
第 4 步：【我的程序】真的执行 get_weather("巴黎")，拿到真实结果
第 5 步：【我的程序】把结果当 role:"tool" 消息（= Observation）拼回 messages，整盘重发
第 6 步：【模型】看 Observation：够了→写人话回答；不够→吐新 Action，回到第 3 步
第 7 步：【我的程序】把回答显示给用户
```

## 三、模型到底有没有真的执行工具？（T3-01 通过标准）

模型没有真的执行工具，模型只负责输出工具的入参，调用和解析都是客户端做的。

> 💡 补充：「模型负责的决策」精确说是两件事——**选哪个工具 + 定什么参数**（合起来就是那段 Action JSON）；之后的解析、调用、把结果拼回去，全是客户端程序的活。

## 四、今天踩的坑（错误理解 → 正确理解）

1. 我以为中间人是模型 → 其实是客户端。
2. 我以为 Agent 是模型 → 其实 Agent = LLM + 工具 + 客户端。
3. 我以为「停止」在输出完结果给用户之后 → 其实是在模型生成完 JSON 的时候就立刻停止。不停的话，模型会把后面的结果给占掉，编出一个错误的结果，实际没有调用工具。
4. 我以为叫「函数调用」就会调用函数 → 模型实际上不调用函数。

> 💡 补充 1（第 1 条的真实轨迹）：当天实际两次错猜是「**工具自己会执行**」和「**平台执行**」，最后才落到客户端——复习抽查时用这两个错误说法当干扰项最有效。
>
> 💡 补充 2（第 3 条的术语）：「被占掉的那个槽位」有名字——**Observation**。事故全称：模型顺着剧本自己编一个假 Observation，格式全对、回答自信，最隐蔽。
>
> 💡 补充 3（第 4 条的右半补全，用的是你上一轮的原话）：模型不调用函数、只生成**调用请求**；「这能力是厂商训练好的」——焊在参数里（肌肉记忆），不是 prompt 临场求来的（临场发挥）。

## 五、名词卡（一行一个，人话解释）

- **Action**：行动，模型行动起来，输出 JSON。
- **Observation**：观察，获取到返回结果后，模型会观察这个信息是否可用，可用就整理输出给用户，不行就继续通过客户端去调用工具。
- **停止并解析（stop and parse）**：在模型行动后（生成 JSON），立刻停止，并让客户端去解析输出的 JSON。
- **Function Calling vs 手搓 prompt 教学法**：Function Calling 等于原装纽扣，手搓 prompt 教学法等于手缝纽扣。Function Calling 是厂商训练好的、模型记在记忆里的；prompt 是后期输入的，模型可能会忘记。

> 💡 补充 1（Action 的精确定义）：Action 不是「模型动起来」，模型动不了——Action 就是**它吐出的那段调用请求 JSON 本身**（选哪个工具 + 什么参数）。「模型唯一的行动方式就是说话」。
>
> 💡 补充 2（Observation 是「东西」不是「动作」）：Observation = 工具的**真实执行结果**（成功数据、报错信息都算），由客户端当新消息（`role:"tool"`）拼回对话。你写的是「模型拿到它之后干什么」，也对，两半合起来最完整。
>
> 💡 补充 3（第 4 条两处措辞校准）：「记在记忆里」→ 更准是**焊在模型权重里**（训练出来的本能，不是记忆）；「prompt 可能会忘记」→ 更准是**不保证遵守**——格式可能吐歪、说明书可能被无视，所以手搓版才需要 `validate_payload` 这类代码兜底。
