## 一、什么是上下文工程（vs 提示工程）

① **「上下文」** = 一次调用模型时、所有进入上下文窗口的**整组 token**；**不止**你写的那句 prompt，还包含：系统指令、工具说明、对话历史、检索资料、记忆等。

② **提示工程 vs 上下文工程 = 跨层 / 演进关系**：上下文工程**包含**提示工程、是它的升级。
- 提示工程＝写好「那一格指令」（措辞、格式、给不给例子）。
- 上下文工程＝策划「整盒（会进窗口的所有 token）」，指令只是其中**一格**。
- （注意：「上下文」是名词＝整组 token；「上下文工程」是对它做的动作＝在推理阶段策划维护最优信息集合。别把两个定义黏一起。）

③ **小坑：`prompt` 有两义。**
- 狭义＝你写给模型的指令文字（本课 / 提示工程用这个）。
- 广义＝模型一次吃进的完整输入（整个 `messages` = system + 历史 + 本轮）。
- 本课统一用**狭义**：上下文 = 系统指令 + 工具 + 历史 + 检索 + 这句指令之和，prompt 只是其中一格。
- 判断某内容算不算上下文，**看它是否会进窗口的 token**，别看名字（`system prompt` 名字带 prompt，但它只是上下文的一格）。

## 二、为什么重要：context rot（核心）

① **context rot（上下文腐蚀）**：随着窗口里 token 增多，模型从中**准确回忆信息的能力反而下降**（"针堆找针 needle-in-a-haystack" 基准测出来）。

② **现象 → 结论**：正因为有 context rot 这个**现象**，才得出「上下文是**有限资源 + 边际收益递减**」这个**结论 / 对策**——多塞 token，关键信息被稀释，收益越来越小；若关键信息被淹没/丢失导致结论错误，收益甚至**变负**。

③ **注意力预算（attention budget）**：模型像人的工作记忆，有一笔有限预算，每个 token 都在花它 → 要谨慎筛选放什么。

④ 是**性能梯度**、不是悬崖（越长越**缓慢**下滑，不是某长度突然崩）。机制（了解即可）：Transformer 每个 token 与其他 token 两两关联，n² 增长 → 太长注意力被**摊薄**；且训练语料短序列多、长上下文经验少。

## 三、有效上下文长什么样（9.2.1）

① **系统提示两极误区**：**过度硬编码**（塞脆弱 if-else、难维护、易碎）/ **过于空泛**（只给大话、缺具体信号）。
- 「**最小 ≠ 最短**」：最小必要信息集是**双向平衡**——**下限**别漏关键信息（别太空 → 否则误判），**上限**别注水（别稀释、腐蚀 → context rot）。恰好覆盖期望行为、一条不多一条不少。
- （相关但不同的另一根轴：「过于空泛 vs 过度硬编码」是**写法/刚性**轴，与「太短/太长」**信息量**轴是**表亲非双胞胎**；过度硬编码核心罪是"脆弱难维护"，不只是"长导致腐蚀"。）

② **工具 MVTS（最小可行工具集）**：职责单一、低重叠、说明清楚；臃肿工具集会让模型纠结"调哪个"。金句：「**如果人类工程师都说不准用哪个工具，别指望智能体做得更好**」。

③ **few-shot**：精选少量**多样且典型**的示例，别罗列所有边界情况。「好的示例胜过千言万语」。

④ 总纲：**信息充分但紧致**。

## 四、压缩 / 筛选上下文的做法 —— 五种手段速查（⭐通过标准核心）

| 手段 | 怎么做 | 属哪一层 | 适用场景 | 代价 / 风险 |
| --- | --- | --- | --- | --- |
| **trim / 截断 truncation** | 历史太长就按位置删最早的（只留最近 N 条） | 上下文工程·最朴素**基础档** | 简单多轮、对早期信息不敏感 | 按**位置**删、**不看重要性** → 可能误删"旧但重要"（如开头的名字） |
| **JIT 及时检索** | 不预载，只放轻量引用（路径/查询/URL），运行时用工具按需读 | 上下文工程·**按需检索类** | 资料超大/超窗口（几百页手册、大代码库） | 比预载**慢**（多次工具来回）、需好工具与引导，否则乱翻浪费 |
| **Compaction 压缩整合** | 接近窗口上限时把对话高保真**总结成摘要**，用摘要**重启新窗口** | 上下文工程·**长时程三件套** | 需**长对话连续性**（接力） | ① 额外调一次模型（钱+延迟）② 摘要可能**失真/丢细节** |
| **结构化笔记** | 关键信息定期写到**上下文外的持久存储**（md/TODO），按需拉回 | 上下文工程·**长时程三件套** | 有**里程碑/阶段成果**的迭代开发与研究；记关键字段（订单号/诉求） | 需维护笔记、读写时机设计 |
| **子代理架构** | 主 agent 规划+综合，子 agent 在各自**干净窗口**深挖、回传 1~2k 摘要 | 上下文工程·**长时程三件套** | **复杂研究/分析**、能**并行**探索（如调研 10 家竞品） | 协调成本、上下文分散、多 agent 风险 |

**三件套选择经验法则**：要长对话连续性 → **Compaction**；有里程碑/阶段成果的迭代 → **结构化笔记**；复杂研究、能并行 → **子代理**。

## 五、接回我的 L1 chatbot `trim_history`

① `trim_history` 属于**裁剪/截断（truncation）**，属于**上下文工程**（**不是**提示工程！提示工程只写指令、不碰删/压历史）。

② 它靠**位置/新旧**决定删谁（删最早的几轮），**不看重要性** → 会误删"旧但重要"的信息（如第 1 轮报的名字），却留着"新但没用"的。

③ vs Compaction 本质区别：`trim`＝**硬删**（旧的直接扔）；Compaction＝**软压**（旧的压成摘要保留梗概）。二者**平级**，都在处理"历史太长"，但 Compaction 能保信息进了长时程三件套，trim 是最朴素档。

## 六、今天踩的坑（错误理解 → 正确理解）

1. **两组对比混淆**：错把「上下文工程 vs 提示工程」当成和「Compaction vs trim」一样 → ✅ 前者是**跨层/演进**（上下文工程包含提示工程），后者是**同层平级**的两种手段。
2. **trim 的归类**：错说"trim 是提示工程的手段" / "不止提示工程也是上下文工程" / "trim 属于 Compaction" → ✅ trim **只**属上下文工程；trim ≠ Compaction，二者**平级**；trim 的技术名是 **truncation**，是上下文工程**最朴素的通用基础档**，不在 9.2.3 长时程三件套里。
3. **Compaction 的两个代价**：① 额外调一次模型（钱+延迟）；② 摘要本身可能**失真/丢细节**（故原文"先保召回、再保精确"）。
4. **切片陷阱**：`history[-0:]` == `history[0:]` == **整个列表**（`-0 == 0`）；若 `keep_recent=0`，trim/compaction 会失效返回全部。
5. **`str.split()` 与 `count_tokens`**：`split()` 按**空格**切**不按字**，"我在学习"整块算 1 个词；该 `count_tokens` 对中英混合会**重复计中文、不精确**（生产用真 tokenizer）。
6. **JIT ≠ 结构化笔记**：按需读大资料是 **JIT**；记"订单号/关键诉求"这种跨轮持久信息用**结构化笔记**（**不是子代理**，子代理是拆复杂任务并行深挖）。

## 七、收口 & 待办

**一句话收获**：上下文工程＝把"会进窗口的整组 token"当**有限资源**来策划；Agent 失败多源于**上下文管理**而非模型本身；`trim_history` 只是众多手段里**最朴素的一种（truncation）**。
