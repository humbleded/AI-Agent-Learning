## 逐题记录

### 1. 删除文件工具的最小权限、确认与审计

- 你的回答要点：删除只允许在沙盒路径内；删除前用户确认；沙盒外拒绝。
- 结论：部分通过。
- 反馈：核心权限边界和确认正确；还需规范化真实路径，防止 `..` 和符号链接绕出沙盒，并记录完整审计事件。
- 标准回答：服务端将删除权限限制在预设沙盒根目录，先解析真实路径并确认仍在范围内。删除前展示目标并要求明确确认，确认后再次校验路径和权限再执行。审计记录请求者、目标、确认、结果和失败原因。

### 2. 用户确认后目标文件不存在

- 你的回答要点：客户端检查路径和文件存在；失败时返回固定格式给 Agent，由 Agent 说明失败。
- 结论：通过。
- 反馈：补充：工具执行状态必须是唯一事实来源，失败时不得由模型误报成功。
- 标准回答：执行前再次校验路径和存在性；不存在时工具返回结构化失败。客户端禁止在失败状态下输出“已删除”，Agent 只能说明目标可能已被移动或删除，并建议刷新后重试。

### 3. 删除保护的测试设计

- 你的回答要点：测试沙盒外路径、未确认删除、目标不存在和空路径。
- 结论：通过。
- 反馈：还应覆盖成功路径、`..`/符号链接绕过、执行异常和最终回复不误报成功。
- 标准回答：分别测试正常删除、权限与路径绕过、确认与输入校验，以及注入失败时的结构化结果、文件真实状态、Agent 回复和审计日志一致性。

### 4. 为什么工具单测通过，Agent 仍可能误报成功

- 你的回答要点：要检查 Agent 是否实际调用工具，以及文件是否真实删除。
- 结论：通过。
- 反馈：已抓住端到端验证的重点。
- 标准回答：除工具返回外，还要断言执行轨迹确有工具调用、真实副作用与工具结果一致、最终用户回复与状态字段一致；组件之间的状态映射错误也会导致端到端失败。

### 5. 待确认操作的服务端状态

- 你的回答要点：保存确认状态和文件路径；目标变化后让旧确认失效。
- 结论：部分通过。
- 反馈：待确认记录还应包含用户身份、操作类型、一次性标识和有效期；“是否删除成功”属于执行后的审计状态。
- 标准回答：每次删除保存用户身份、操作类型、规范化目标路径、一次性请求标识、确认状态和有效期。执行前再次核对，文件变化、过期或重复使用均拒绝；结果另写审计日志。

### 6. 超时后的重复确认

- 你的回答要点：查询请求状态，利用一次性标识和有效期避免重复。
- 结论：部分通过。
- 反馈：还需用原子状态转换解决并发重复请求。
- 标准回答：用幂等键标识一次删除，把状态原子地从“待执行”改为“执行中”；只有成功转换的请求能执行。重复请求返回已保存的进行中或最终结果，避免重复副作用和误报。

### 7. 幂等键的安全边界

- 你的回答要点：尚未掌握幂等键概念；提出服务端校验请求标识。
- 结论：需要复测。
- 反馈：已完成概念讲解；下次应能独立说明它不是权限凭证。
- 标准回答：幂等键是一次操作的唯一编号，用于让重复请求只产生一次效果。服务端必须把它绑定到用户身份、操作类型、目标资源和有效期；身份或资源不匹配就拒绝。

### 8. 工具结果为什么要回到模型上下文

- 你的回答要点：这是 ReAct；模型据工具结果判断目标是否完成，未完成则继续，完成则整理回复。
- 结论：通过。
- 反馈：ReAct 闭环清楚。
- 标准回答：工具结果是模型下一步决策的事实依据；模型据此继续行动或组织最终解释。客户端直接结束只能得到原始数据，丢失综合判断、多步推进和自然语言回答。

### 9. 清洗过大的工具返回

- 你的回答要点：只保留需要字段，减少上下文长度、成本和注意力分散。
- 结论：通过。
- 反馈：广告、调试字段和无关预报应过滤掉。
- 标准回答：客户端先确定性清洗和结构化提取，只保留当前任务需要的字段，过滤冗余、调试和敏感信息，降低成本与干扰。

### 10. 长对话的上下文管理

- 你的回答要点：全部历史会耗尽窗口并造成干扰；使用压缩摘要、结构化笔记和渐进式披露。
- 结论：通过。
- 反馈：上下文工程理解稳定。
- 标准回答：保留系统规则、当前任务、近期对话与必须精确保留的信息；把较早稳定结论压缩为结构化摘要或长期笔记，按当前任务检索相关片段，而非全量加载。

### 11. 聊天历史、长期 Memory 与 RAG 的区别

- 你的回答要点：聊天历史用于会话线索；长期记忆存重点；检索文档按需读取并节约上下文。
- 结论：部分通过。
- 反馈：长期 Memory 不应每次全量加载；RAG 的主作用是外部知识和可追溯证据，不只是省上下文。
- 标准回答：聊天历史是当前会话的短期工作上下文；长期 Memory 是跨会话的稳定用户或任务信息；RAG 是按当前问题从外部文档检索证据。三者的来源、生命周期、权限和可信度不同。

### 12. 户外活动安排中组合 Plan-and-Solve 与 ReAct

- 你的回答要点：先用 Plan-and-Solve 做整体规划，遇到天气变化后由 ReAct 调整并重规划。
- 结论：通过。
- 反馈：模式选择正确。
- 标准回答：Plan-and-Solve 拆解目标、天气、日历和候选方案；ReAct 调用工具并根据实时结果局部调整或重规划。写入日历前必须展示方案并取得用户确认。

### 13. 新偏好导致活动安排变更

- 你的回答要点：重新规划，保留失败原因，重新调用天气和地点工具。
- 结论：部分通过。
- 反馈：用户是新增约束而非原计划失败；要保留原目标、计划、约束和查询结果。
- 标准回答：将“不晒太阳、不占晚上”加入现有计划约束，查询小时级天气和日历空闲，生成候选方案。无解时说明冲突并请用户放宽条件；写日历前确认。

### 14. 无可行方案时为何停止

- 你的回答要点：设最大尝试次数；无解时说明原因并请用户换时间。
- 结论：通过。
- 反馈：停止条件意识稳定。
- 标准回答：设置最大步数、时间或调用预算；合理候选已覆盖或到达上限时停止，不编造方案，说明冲突并让用户选择放宽哪个约束。

### 15. 简单计算是否总要调用工具

- 你的回答要点：模型是预测式的，担心“一加一”也可能答错，因此倾向每次调用计算器。
- 结论：需要复测后通过。
- 反馈：风险意识正确；需要按业务风险、正确性、成本和延迟权衡，而不是机械地总调用或总不调用。
- 标准回答：普通低风险简单计算可直接回答；复杂、精度要求高、用户要求核算或模型不确定时调用计算器。财务等高风险场景应优先正确性与可审计性，即使简单也调用可验证工具。
