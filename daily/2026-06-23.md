# B3 甲(请求没发出去) vs 乙(服务器返回错误响应) 代码里各靠什么发现 + 为什么 except 只抓甲不抓乙
答（手段）：甲靠 except 抓异常；乙靠 response.ok / response.status_code 主动判断。
答（为什么，经两次订正）：
  - requests 真正的任务 = 把客户端请求发出去 + 接收服务端的回信；
  - 乙(404) 这次「发」和「收」都完成了（收到了回信），任务成功 → 所以不抛异常，正常返回 response；
  - 404 算不算错误，requests 不管，把判断权交给开发者（你自己看 status_code/ok）；
  - 甲是连回信都没收到（DNS/连接/超时，网络层就失败），requests 没法完成任务 → 才抛异常。
判定：RETRY→PARTIAL→PASS
中间坑：
  ① 第一版把乙的原因窄化成「只能说明请求参数有问题」——其实 404 多是资源/路径不存在、5xx 是服务端的锅，都不必是参数。
  ② 第二版把「requests 的任务」误选成「替我判断响应对错」，与「它不抛异常」自相矛盾
     （若它判断对错、又判出 404 是错，就该抛异常了，但实际没抛）。
  ③ 反证法点破：它不抛异常→说明它认为成功了→反推它的任务不是判断对错，而是「发请求+收回信」，完成即成功。
```

# C4 写码：classify_status(code) 返回五大类
答（终版）：
def classify_status(code):
    code = int(code) // 100      # 整除取首位段
    if code == 1: return "信息"
    elif code == 2: return "成功"
    elif code == 3: return "重定向"
    elif code == 4: return "客户端错误"
    elif code == 5: return "服务器错误"
    else: return "未知状态"
判定：RETRY→PASS
中间坑：第一版用 / 真除法（int(code)/100），导致非整百状态码漏判——
  404/100=4.04，4.04==4 为 False，所有 elif 都不匹配 → 错误地返回「未知状态」；
  只有恰好整百(200/300/400)才碰巧 == 整数。改用 // 整除（404//100=4）后命中正确分支。
易错点：/（真除法得 float）vs //（整除得 int）——分类/取整段要用 //。
小瑕疵（不扣分）：返回「服务器错误」与题目「服务端错误」字面不一致；可用新变量名 category=code//100 避免覆盖参数。
```

# C5 读码+为什么：resolve_ip 失败 return None 的好处 + fetch 怎么用
答（好处）：返回 None 给调用方一个明确的「没拿到 IP/失败」信号，调用方一个 if not ip 就能判空处理；
