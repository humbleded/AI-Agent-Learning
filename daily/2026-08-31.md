### StateGraph 第一片段｜从零件到可编译的工作流设计

本片段实际读取范围是本地“状态图（StateGraph）”第 83～105 行，只覆盖 builder、Node/Edge 登记和 `compile()`；原文后面的可视化与 `invoke` 示例留到 G5 闭合后的下一片段。

核心关系：

```text
IncidentState（共享数据格式）
          │
          ▼
StateGraph builder（设计和组装工作流）
   ├─ add_node：登记图内名称 → Python 函数
   ├─ add_edge：登记固定路线
   └─ add_conditional_edges：登记动态路线
          │
          ▼ compile()
CompiledStateGraph（可执行图，才有 invoke/stream 等运行接口）
```

边界：`StateGraph(IncidentState)` 接收的是 State 的格式定义，不是某次运行的初始字典；`add_node` 只是注册，不会当场执行函数；`compile()` 做基础结构检查和装配，不会调用模型或工具，也不等于业务逻辑已经正确。若编译后再修改 builder，旧的 compiled graph 不会自动获得变化，需要重新 `compile()` 生成新的执行对象。

#### 1. `invoke()`：给可执行 Graph 一份初始输入，等它走到本次运行结束

当前关系如下：

```text
初始输入字典
    │
    ▼
START → 第一个 Node
              │ 返回局部更新
              ▼
       LangGraph 合并到 State
              │
              ▼
       Edge / 路由读取最新 State
              │
              ▼
        后续 Node 或 END
              │
              ▼
       invoke() 返回最终输出
```

`invoke()` 是同步调用：正常情况下，当前 Python 调用会等待这次 Graph 执行结束，再得到返回值。后一个 Node 读取的不是最初那份 State，而是前面 Node 的局部更新已经合并后的最新 State。

当前项目只使用 `StateGraph(IncidentState)`，没有单独声明 `input_schema` / `output_schema`，所以可把下面的 `result` 理解为最终完整 `IncidentState`：

```python
result = compiled_graph.invoke(initial_state)
```

这是当前设计下的结论，不是“所有 LangGraph 永远返回全部内部 State”：以后若显式设置更窄的 `output_schema`，返回字段可被限制。这个例外本片段只定位，不展开实现。

教材中的字符串之所以逐步变长，是 Node 自己读取旧字符串并拼接新字符串后再返回；没有自定义 reducer 时，LangGraph 对该字段仍按默认规则覆盖，并不会自动替 Node 追加字符串。

#### 2. 返回值、控制台打印与中间过程不要混在一起

教材里的两类输出来源不同：

- `---Node 1---` / `---Node 3---` 来自 Node 内部的 `print()`，是控制台副作用；它们没有自动进入 State。
- 最后的字典才是 `invoke()` 返回值。Notebook 会自动显示代码单元最后一个表达式的值；在普通 `.py` 文件里，单独写 `compiled_graph.invoke(initial_state)` 不会自动把字典打印到终端，需要赋值后 `print(result)`。

普通 `invoke()` 让调用方最终拿到本次结果，不逐条向调用方交付每个 Node 的中间更新；如何边运行边看到更新，留到下一阶段的 `stream()` 片段。

### Streaming 基础片段｜运行过程中逐步收到 State 变化

本地中文 LangGraph 单元没有 `stream()` 示例，因此本片段完整读取当前官方 Streaming 文档的“Get started / Graph state”基础范围，只覆盖同步 `stream()`、v2 chunk、`updates` 与 `values`；模型 token、异步、custom、subgraph、checkpoint/debug 等明确延期。

#### 1. `stream()` 是什么

`invoke()` 与 `stream()` 都会执行 Graph，但调用方拿到信息的时间不同：

```text
invoke(initial_state)
    → 执行完整 Graph
    → 结束后一次返回最终结果

stream(initial_state, ...)
    → 启动一次新的 Graph 运行
    → 返回可迭代结果
    → for 循环在运行过程中逐块取得 chunk
```

这里的 **chunk** 就是一次流式产出的“小包数据”。`stream()` 不是读取上一次 `invoke()` 的录像；如果先调用一次 `invoke()`，再调用一次 `stream()`，就是两次独立执行，Node 和工具也可能各执行两次。

当前采用官方主示例的显式 v2 格式：

```python
for part in compiled_graph.stream(
    initial_state,
    stream_mode="updates",
    version="v2",
):
    if part["type"] == "updates":
        print(part["data"])
```

每个 v2 `part` 都有统一外壳：

```python
{
    "type": "updates",
    "ns": (),
    "data": {
        "node_name": {
            "changed_key": "new_value",
        },
    },
}
```

- `type`：本 chunk 属于哪种流式模式。
- `ns`：它来自哪一层 Graph；当前没有子图，所以根 Graph 是空元组 `()`，子图路径以后再学。
- `data`：真正要看的内容，具体形状由 `stream_mode` 决定。

当前默认仍是 v1；单一模式下 v1 直接给原始数据，没有统一的 `type / ns / data` 外壳。本任务显式写 `version="v2"`，避免代码依赖默认版本，也方便后续用 `type` 区分不同流式数据。G6 的 `invoke(initial_state)` 没传 `version`，仍使用默认 v1 并返回普通最终 State 字典，与这里不冲突。

#### 2. `updates`：只看“这个 Node 刚改了什么”

假设有一个与当前题不同的最小 Graph：

```python
class DemoState(TypedDict):
    count: int
    status: str

def add_one(state: DemoState):
    return {"count": state["count"] + 1}

def mark_done(state: DemoState):
    return {"status": "done"}
```

初始 State 是：

```python
{"count": 0, "status": "pending"}
```

使用 `stream_mode="updates"` 时，两次 `part["data"]` 分别是：

```python
{"add_one": {"count": 1}}
{"mark_done": {"status": "done"}}
```

可以看到，`updates` 包含：

- 哪个 Node 完成了更新；
- 该 Node 返回的局部 State 更新。

它不会在每个 chunk 中重复没改过的字段，因此适合任务要求的“state/node 更新流”。但它也不是自动脱敏器：如果 Node 把敏感日志放进返回更新，stream 同样可能把它交给调用方，应用代码仍要控制哪些字段可以对外暴露。

条件路由函数如果只返回下一节点名、不返回 State 更新，而且没有注册成业务 Node，就不会单独产生 `updates` chunk；`START` 和 `END` 也不会因为只是入口/终点标记而产生业务更新 chunk。

#### 3. `values`：每一步都看“现在整份 State 是什么”

同一个 Demo Graph 改用：

```python
stream_mode="values"
```

每个 `part["data"]` 都是完整 State，而不是局部更新：

```python
{"count": 0, "status": "pending"}
{"count": 1, "status": "pending"}
{"count": 1, "status": "done"}
```

官方基础示例会先发初始完整 State，再发每一步更新合并后的完整 State。因此：

```text
updates → 谁刚改了哪些字段
values  → 每一步结束后整份 State 长什么样
```

完整 State 通常更直观，但 State 很大时也会产生更多重复数据；当前只按观察目标选模式，不把性能优化扩成新课。

#### 4. Graph 状态流不等于模型逐 token 输出

当前学习的：

- `updates`：Graph 每一步的局部 State 更新；
- `values`：Graph 每一步的完整 State。

它们都不是 LLM 一个字、一个 token 地输出文本。官方把模型 token 流放在 `messages` 模式；本任务只要求至少一种 state/node 更新流，因此先把 `updates` 做稳，`messages` 留到真实模型和交付接口出现后再按需要处理。

`stream()` 也不等于持久化：chunk 被交给当前调用方，并不代表它被保存成 checkpoint；进程恢复仍属于 G8-01～03。

### 工具分支片段｜模型提议动作，应用代码批准并执行

本地教材的核心代码是：

```python
tools = [divide, extract_text]
llm_with_tools = llm.bind_tools(tools, parallel_tool_calls=False)

builder.add_node("assistant", assistant)
builder.add_node("tools", ToolNode(tools))
builder.add_conditional_edges("assistant", tools_condition)
builder.add_edge("tools", "assistant")
```

这段代码表达四个不同职责：

```text
模型 Node
  │ 生成 tool call（提出工具名与参数）
  ▼
条件路由
  │ 有工具请求才进入执行分支
  ▼
ToolNode / 自定义工具 Node
  │ 应用侧真正执行已登记工具，并产生结果或失败
  ▼
State / ToolMessage
  │ 后续 Node 读取结果
  ▼
继续分析、得出结论或确定性停止
```

#### 1. `bind_tools` 不是执行，也不是把授权交给模型

`bind_tools(tools)` 把工具名称、说明和参数格式提供给模型，使模型能够输出结构化工具请求。模型的输出只是“建议调用哪个工具、使用什么参数”；应用代码仍要决定：这个名称是否在白名单、参数是否合法、当前身份和业务状态是否允许、是否真的执行。

#### 2. `ToolNode` 是通用执行器，但不是业务停止规则

`ToolNode([...])` 是已经实现好的工具执行 Node，适合以消息和 `tool_calls` 为主的通用 Agent 循环。它能查找已登记工具、执行调用并生成对应工具结果，还支持并行执行和 State/context 注入。

但它不会自动理解当前项目里的业务字段：一次工具异常是否应设置 `tool_failed=True`、错误对外显示什么、是否立即停止、是否允许重试，仍要由应用明确规定。当前 reference 的默认错误策略也不能理解为“所有工具执行异常都会自动变成可继续的结果”：参数/工具请求类错误可转成消息，实际工具内部抛出的异常默认仍可能向外传播；需要自定义错误处理或外层业务 Node 做映射。

#### 3. 本项目 v1 为什么先用自定义工具 Node

当前流程已经有清楚的业务 State：`evidence`、`tool_failed`、`tool_error`、`step_count`，并且只允许少量只读诊断。第一版直接使用代码白名单更容易观察和测试：

```python
APPROVED_READONLY_TOOLS = {
    "get_recent_errors": get_recent_errors,
    "get_latency_summary": get_latency_summary,
}
```

`run_readonly_diagnostic` 只允许从这个字典取函数。模型即使输出 `restart_service`、`delete_logs` 或一个根本不存在的名称，也只能被拒绝，不能通过字符串名称动态寻找和执行任意函数。

当前固定路线仍是：

```text
review_evidence
  └─ 需要更多证据
       → run_readonly_diagnostic
       → review_evidence
       → route_after_review
            ├─ tool_failed=True → tool_failure_stop
            ├─ evidence enough → build_conclusion
            └─ 其他有限分支
```

成功时，工具 Node 把已经校验的证据显式写回 `evidence`；失败时，写入稳定的 `tool_failed` 和 `tool_error`。不能像本地旧示例那样捕获异常后只返回空字符串，否则后续无法分清“工具成功但没查到证据”和“工具根本没有成功执行”。

工具返回普通字符串或对象，也不意味着它已经自动更新当前自定义 State；在本项目中，仍由 Node 把已校验结果投影成明确的局部 State 更新。`evidence` 当前没有 reducer，因此要保留旧证据时，Node 必须自己构造包含旧证据和新证据的新列表，再由默认覆盖规则写回。
