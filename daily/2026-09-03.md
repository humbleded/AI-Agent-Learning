#### `G8-00-I3`｜证据审查 Node

当前在做什么：实现纯 Python Node `review_evidence(state)`。它读取当前已经收集的 `evidence` 以及原始 `alerts` / `logs`，把审查结果投影成结构化字段，供后续确定性路由读取。

为什么需要这一步：`organize_facts` 只整理事实，后续条件路由只应该读取有限状态，而不应该重新猜测任意文本。I3 位于二者之间，负责回答“证据已经够了、完全没有可诊断信号，还是应提出一次只读工具请求”；它只形成请求，不拥有工具执行权，也不负责最终停止。

本 v1 固定三个互斥分支，按以下优先级判断：

1. `evidence` 非空：返回 `{"evidence_status": "enough", "requested_tool": None}`。这一分支优先，即使 `alerts` 和 `logs` 都为空，只要已经有证据就仍是 `enough`。
2. `evidence` 为空，并且 `alerts`、`logs` 也都为空：返回 `{"evidence_status": "insufficient", "requested_tool": None}`。
3. `evidence` 为空，但 `alerts` 或 `logs` 至少一个非空：返回 `{"evidence_status": "unknown", "requested_tool": "get_recent_errors"}`。

职责边界与完成标准：

- 只读取 `evidence`、`alerts`、`logs`，返回值必须恰好包含 `evidence_status` 和 `requested_tool` 两个键。
- 不原地修改输入 State，不调用任何工具，不读取或更新 `step_count`，也不决定下一个 Node。
- `enough` 和 `insufficient` 都必须显式把 `requested_tool` 清成 `None`，避免旧请求残留。
- 只有一条 alert 或只有一条 log 时都属于第三分支；工具名必须精确为后续白名单将登记的 `get_recent_errors`。
- 当前 v1 只用“证据列表是否非空”验证控制流，不在 I3 扩展证据内容质量判断；工具成功但没有新增证据时会继续是 `unknown`，以后由路由的 `max_steps` 上限兜底。

#### `G8-00-I8b`｜正常路径 invoke 与 v2 updates stream 骨架

当前在做什么：给已经编译成功的 Graph 增加两个很薄的调用入口。`invoke_incident()` 启动一次完整运行并返回最终 State；`stream_incident_updates()` 启动另一次新运行，在每个 Node 完成后立刻把其局部更新交给调用方。

```python
    graph = build_incident_graph(generate_text=generate_text)
    return graph.invoke(initial_state)


def stream_incident_updates(
    initial_state: IncidentState,
    *,
    generate_text: Callable[[str], str] = request_deepseek_conclusion,
) -> Iterator[UpdatesStreamPart]:
    graph = build_incident_graph(generate_text=generate_text)
    yield from graph.stream(
        initial_state,
        stream_mode="updates",
        version="v2",
    )
```
