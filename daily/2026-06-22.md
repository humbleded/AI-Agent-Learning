```python
# B4 角色扮演（人设+全局规则）放哪个 role？为什么不是另两个？
答（一次）：放 system，system 优先级最高。
追问（user/assistant 为什么不行）：user 装本轮问题+历史+system，塞进 user 每轮带着造成上下文长/token 浪费，它只管本轮一次；assistant 是模型的回答，放人设不行。
判定：PARTIAL→PASS
中间坑：把「user 这个 role」和「发出去的整盘 messages」搞混——以为 user 格子里装着 system+历史。其实整盘 = system 消息 + 历史(user/assistant 一来一回) + 本轮 user；user 这个 role 只装「用户说的话」，system 是独立的格子，不在 user 里。
订正：不放 user 的两条硬理由——① 优先级 system>user，人设是全局铁律放 system 才压得住；② 作用范围，user 只对那一轮生效，想「固定」整段就得每轮重发（token 浪费是这个的副作用、不是主因），放 system 一次管全程。assistant 装「模型说过的话」，写人设=替模型伪造发言、不是指令。
口诀：system/user/assistant 是「谁说的」三个格子；角色扮演是「话怎么写」的技巧——技巧内容放进 system 格子，但技巧 ≠ 格子（弱点③）。
```

```python
# B5 指令调优 vs few-shot：谁改了模型、训练时还是用的时候
答：(a) 指令微调（指令调优 / Instruction Tuning）。
(b)（一次）指令调优=把本事永久焊进模型、训练时就大量练好，能直接用大白话对话——只说透了指令调优半边。
追问后补 few-shot 半边：不改模型本身、在用的时候（推理时）给示例，只有这次有效、下次不记得。
判定：PARTIAL→PASS
区别（两边对照）：指令调优改「模型权重」（训练期，一次练好人人受益、永久）；few-shot 改「这一次的 prompt」（推理期，临时/这次性，下次不带就忘，且每次带示例都占 prompt_tokens）。一句话：指令调优改「模型」，few-shot 改「这次的 prompt」。
中间坑：又踩弱点①「区别要两边对照」——先只答了一边（指令调优），补上 few-shot 才完整。
```

```python
# D1 必答③：prompt 何时越长反而越差（短版 vs 塞无关科普的长版翻译）
答：1. 太长会让模型"忘记"最初目标，无关信息太多掩盖主要目标。2. 计费含输入+输出，越长越贵。
判定：PASS
补：原因1含两个效应——①稀释：无关内容把核心指令"浓度"冲淡；②淹没/lost-in-the-middle：超长上下文里关键信息(真正的指令)易被忽略。原因2=token 成本（接 L1-05：输入算 prompt_tokens，越长越贵，还更慢/延迟高）。
关键结论(必答③落点)：不是"长 prompt 一定差"，而是"塞了无关/冗余内容才差"。长但全相关有用(必要 few-shot、清晰约束)是好的 → 笔记第5节「长≠好，相关+清晰才好」。
```
