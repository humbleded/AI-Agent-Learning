## 带读与即时考察

### G1｜LLM 是否是固定问答字典；参数量意味着什么

原始作答：

> 不对，如果是字典的话，LLM 就只会根据固定的问题生成固定的回答；LLM 训练是通过大量训练，让模型理解语法语义，并根据训练文本预测下一个概率最高的 Token。训练时参数越多，模型理解能力越强。

订正与补充：

- “不是固定字典”和“预测下一个 Token”的方向正确。
- 参数量表示模型设计时固定的可学习参数规模和容量，不等于能力必然更强；能力还受到训练数据、训练方法、计算资源和模型结构影响。

用户订正：

> 1. 参数是在模型设计时就固定的，参数大，能容纳的规律就越多。
>
> 2. 能力还和训练的数据、训练方法、计算资源和模型结构有关，所以不能说参数大，模型就一定强。

单题状态：`PARTIAL → PASS`

### G2｜Encoder / Decoder / Encoder-Decoder

原始作答：

> A = 编码器，因为需要根据内容判断属于哪种分类。
>
> B = 解码器，因为需要根据问题生成回答，需要生成新的 Token 序列。
>
> C = 编码器-解码器，因为需要先理解中文，再生成语义相似的英文 Token 序列。

订正与补充：三类任务侧重判断正确；“理解/生成”是便于入门的功能比喻，不代表 Encoder 完全不会输出表示或 Decoder 不会利用上下文。

单题状态：`PASS`

### G3｜Token 与 EOS

原始作答：

> Token 不一定等于一个完整单词，取决于 Tokenizer；一个单词可能对应一个 Token，也可能对应多个 Token。EOS 不是展示给用户的句号，而是模型用于判断序列结束的特殊 Token。

订正与补充：理解正确。Token 划分取决于具体 Tokenizer；EOS 是控制序列边界的特殊标记，不等于自然语言标点。

单题状态：`PASS`

### G4｜Prompt 为什么能改变输出

第一轮作答：

> B 中更关注邮件属于哪种分类，然后把内容解码成 Token，跟相似的 Token 比较，再输出改写后的 Token。

订正：模型不是从词库里寻找“相似 Token”直接比较。Tokenizer 先把输入转成 Token 序列，模型结合整个输入上下文为候选下一个 Token 打分。

用户订正：

> B 把内容通过 Tokenizer 转成 Token 序列，模型根据整个输入为候选 Token 打分，再输出符合任务要求的新 Token。A 和 B 的模型参数没有改变；提示词不同会改变模型对输入 Token 的侧重，并影响候选 Token 的分数。

单题状态：`RETRY → PASS`

### G5｜注意力能否读取上下文外的工具结果

原始作答：

> 模型不能仅靠注意力机制读取工具结果，因为没有放入上下文窗口，模型不知道 Observation 是什么。注意力不能获取上下文中不存在的结果。

订正与补充：正确。注意力只在当前模型输入表示之间建立联系；工具结果必须由客户端作为消息回填，模型下一轮才能使用。

单题状态：`PASS`

### G6｜指令微调与工具调用

原始作答：

> 微调教会模型生成调用工具的结构；微调改变输出格式并改变模型参数；客户端程序负责真实执行工具。

订正与补充：职责边界正确。指令数据是训练样本，指令微调是用这些数据更新模型参数的训练过程，两者不是同一个概念。

单题状态：`PASS`（Instruction Data vs Instruction Tuning 仍需换场景迁移）

### G7｜生成 Action 不等于真实执行；无状态与危险确认

原始作答摘录：

> LLM 生成了删除请求，但客户端没有解析和实际调用工具，所以不会真的删除。
>
> 服务端是无状态的，需要客户端把历史信息拼接到这次请求中。
>
> 仅靠系统消息不能保证文件一定不会被删除，客户端还需要代码校验；没有明确用户确认就拒绝执行删除。

订正与补充：工程链路正确。模型生成的是 Action / Tool Call 请求；客户端负责解析、确认、硬校验和执行，工具返回值再被回填为 Observation。

单题状态：`PASS`

### G8｜Chat Template 为什么不能随便换

原始作答：

> 跟模型训练时匹配的聊天模板不一致，可能导致模型把错误标记当成普通文字 Token。错误模板会破坏角色或消息边界，模型不知道从哪开始、到哪里结束。

订正与补充：核心正确。模板把结构化 messages 序列化为模型训练时熟悉的 Token 序列；角色标记、消息分隔和结束标记不匹配会破坏输入分布与边界。

单题状态：`PASS`

### G9｜幻觉、Agent 风险与安全收口

第一轮作答：

> 内在幻觉，因为真实工具返回的结果是失败，但是模型却说成功了。如果客户端把这句话当成真实状态继续执行，后续程序判断可能会出错。

订正：分类正确，但风险需要具体到“错误状态 → 错误动作 → 业务后果”。

用户补充：

> 如果返回的是错误信息，模型却说成功，本来不可以扣款，但因为模型返回的状态是成功，可能就扣款了。

超时分支第一轮已搭对正常工具链，但只说“返回失败提示”；经订正后，用户明确：

> 如果查询超时，只有重试策略允许时才进行有限次数的重试；失败就停止查询。LLM 应告诉用户“目前无法确认订单状态”，不能把超时猜成成功、失败或其他具体状态。

订正与补充：`timeout` 权威证明的是本次查询超时，底层订单状态仍然未知；模型输出不能覆盖订单 API 的结构化结果。

单题状态：`RETRY → PASS`
