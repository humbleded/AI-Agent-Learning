## 后端双实例与 Jenkins 并行构建

目标是在同一个 Nginx 入口把可分流的请求送到两个 API 实例，并让 Jenkins 可以把构建任务分给多个执行位置。这是工作台运维练习。

用户此前在 Windows 上观察到了两个后端交替处理请求。这次由助手核对腾讯云起点：现有 API 只有一个容器，Nginx 把请求送到 `api:8765`。主机有 2 个逻辑 CPU、3.6 GiB 内存，检查时可用约 1.8 GiB。前后端发布程序都按单个 API 容器核对版本。

用户在云端手动启动第二个 API。截图记录原实例 `172.18.0.3`、第二个实例 `172.18.0.5` 的健康响应均为 `ok`，模块状态为 `available` 和 `ready_to_run`。第二个实例第一次请求在 5 秒后超时，随后重试成功。助手从前端容器内按两个名字复查，两者均响应，镜像 ID 相同，重启计数均为零。

## Jenkins 的两个执行位

用户在 Jenkins 的 `workbench-linux` 节点配置中将执行位从 1 改为 2，助手从控制器读回 `numExecutors=2`。两条作业均使用这台节点，两个工作区检出的提交均为 `f6b9be7c204fef00e29bafc40b19f7148148c0e9`。这一项配置证明节点能接两个任务，镜像是否同时构建另以 Docker 命令的实际起止时间验收。

上线前发现前端的 `base` 和 `promote` 都用立即失败的非阻塞锁。有两个执行位后，连同时查询线上版本也可能让前端退出。用户安装只改这一行的前端发布程序。验收时用操作系统锁信息确认两个 Jenkins 账号下的查询均在等同一把发布锁，释放后两个查询成功，三个生产容器身份与启动时间一致。助手读回安装后的程序校验值为 `cf0ec9232ac44fbc976baa39a2c8b8ea19a1d44f88b93410f498a43113906b49`。

用户在两个真实作业的 Replay 页面启动并行验收。前端 #13 在从 GitHub 取代码时失败。后端 #9 已检出 `main`，助手通过 Windows 直接查询 GitHub 的同一分支，确认完整 SHA 一致，准备了同机的临时 Git 副本。用户只重放前端，#14 使用该副本取得同一提交。两个工作区各自生成测试镜像。真实 `docker buildx build --load` 命令开始后计时，两边都从操作系统观察到另一个构建进程同时存活。
