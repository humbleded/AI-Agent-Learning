### `A4-Gate-REFINE-G2`｜JSON / validator 新失败面的恢复分类

- 当前在做什么：只判断 Refinement 相比既有 Candidate / Reflection 多出来的 JSON 与最终 validator 失败，是否值得消耗唯一一次模型 recovery；本检查点仍不写代码。
- 为什么需要：`G1` 只回答了“有资格恢复时还有没有 step”；如果不先定义资格，代码可能把程序 bug 吞成 `needs_manual`，或漏掉一次确实可能由全新模型输出修好的机会。
- 已承认的 PASS 证据，不重复考察：
  - Provider/API 仍复用既有分类：timeout、connection、408 / 409 / 429 / 5xx 是 recoverable；其余冻结状态 fail-closed。
  - Candidate / Reflection 响应仍复用既有分类：坏外壳、坏 / 空正文、`length`、意外 Tool Action 是 recoverable；`content_filter`、`insufficient_system_resource`、缺失 / `None` / 错类型 / 未知 `finish_reason` 是 terminal。Refinement 直接迁移这套守门，不要求用户换阶段名重答。
- 三种标签：
  - `R`（recovery eligible）：丢弃本次坏候选；只有仍有 step 时，才允许再发唯一一次模型请求。`R` 不代表接受坏结果，recovery 返回后仍必须再次通过 `validate_success_result()`。
  - `S`（controlled stop）：不发 Refinement recovery，由公开入口安全映射为 `needs_manual`。
  - `P`（programming / invariant error）：这是调用方输入或程序不变量坏了，不得冒充模型输出失败，也不得悄悄映射为正常的 `needs_manual`；保留原异常向上暴露以便修 bug。

### `A4-Gate-HITL-G1`｜确认必须精确绑定本次动作

HITL（human-in-the-loop，人在回路中）在本块的新增含义不是“再问一句你确定吗”，而是客户端在真实副作用前暂停，并只接受一份能证明“人工允许的正是当前这次动作”的确认。这个约束称为 **action-bound confirmation（动作绑定确认）**：它像一张写明本次请求、工具和参数的授权单，不能拿旧授权单去执行参数已经变化的新动作。

冻结下面这次待执行动作：

```python
planned_action = {
    "request_id": "req-current",
    "tool_name": "fake_delete_source",
    "arguments": {"relative_path": "sample.txt"},
}
```

候选设计 A 只传一个 `confirmed=True / False`；候选设计 B 传一份精确确认对象，例如：

```python
confirmation = {
    "decision": "allow",
    "request_id": "req-current",
    "tool_name": "fake_delete_source",
    "arguments": {"relative_path": "sample.txt"},
}
```

用户需要一次回答：

1. 选择 A 或 B 作为当前 Gate 的最小合同。若选 A，必须说明调用边界怎样保证这个布尔值只能授权同一次、同参数动作且不能被复用；若选 B，说明哪些字段必须与 `planned_action` 精确匹配。
2. 分别给出四条轨迹的行为：精确匹配的 `allow`、精确匹配的 `deny`、没有 confirmation、以及 request ID 或参数不匹配的旧 confirmation。每条只需说明：fake 工具调用次数、是否新增一次真实 `tool_call` step / 日志、客户端是继续执行还是安全停止。
3. 本场景在确认门前没有取得任何真实资料来源。安全停止若公开为固定三字段结果，写出应使用的 `status`，并说明 `sources` 应是什么。

非协商安全条件：没有一份对当前动作有效的明确 allow，就不得产生副作用；任何 deny、缺失或错绑确认都不能依靠 truthiness 放行。当前只做行为决策，不写代码；完成标准是确认表示法能证明授权对象、四条轨迹的调用 / 账本因果一致，并与固定三字段人工接管合同一致。
