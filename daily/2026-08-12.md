### 新概念：请求运行上下文（run context）

- 它是什么：客户端为一次请求创建的一本“小账本”，里面放同一个 `request_id`、当前累计 `step` 与本请求的 `logs` 列表。
- 它有什么用：后续五个模型 / 工具调用都拿到同一个字典对象，才能证明它们属于同一请求、共享同一个步数上限，而且日志不会串到另一个请求。
- 边界：这里的 `context` 是 Python 客户端运行状态，不是 LLM 的 context window，也不会被自动放入 prompt。
- `request_id`：用于把同一请求的多条事件串起来的非空标识。`uuid.uuid4().hex` 可在本地生成随机字符串；测试可以显式注入 `"req-test"` 获得确定结果。

#### 用户追问：这个功能有什么作用？

- 用户原始问题：`这个功能有什么作用？`
- 针对性讲解：`create_run_context()` 本身不执行 Agent 工作，而是在合法请求进入模型 / 工具链前创建一次请求专属的共享状态。`request_id` 负责日志归组，`step` 负责统一调用预算，`logs` 负责保留调用、耗时与错误证据；五个调用点共享同一个字典对象，另一个请求必须创建另一个对象。
- 防错边界：若每个函数自己建 context，同一请求会被拆成多本账；若使用模块级全局 context，不同请求会串 ID、串步数、串日志。初始化本身不是模型 / 工具调用，因此 `step` 从 0 开始、`logs` 为空，不伪造事件。
- 与后续产物的关系：下一检查点会在真实副作用前从同一本账占用 step；后续日志 helper 才把七字段事件追加到 `logs`；外部业务结果仍保持精确三字段，不把内部调试信息混入 `status/summary/sources`。

#### 追问校准：追踪编号不等于防重复

- `request_id` / correlation ID 的职责是“这次执行是谁”：用户重发两次时，只要每次创建新 context，就能把两次执行及其日志区分开。
- 但当前 `create_run_context()` 每调用一次都会创建一份新状态；它不查询历史记录、不保存已完成结果，也不在副作用前检查相同逻辑请求，因此两次重发仍会执行两次。能区分，不等于能阻止。
- 真正的防重复机制称为幂等（idempotency）：客户端对同一个逻辑操作重试时携带同一个 `idempotency_key`，服务端必须把这个 key 持久化，并在执行副作用前原子检查“已完成 / 进行中 / 未见过”。仅有一个字符串字段而没有查重与结果复用，仍不构成幂等。
- 对话级关联还可能使用 `conversation_id/session_id`；它负责把多轮消息归到同一段对话，也不等于一次 Agent 执行的 `request_id`。
- 当前范围：A4-Gate V1 是只读研究摘要 Agent，本检查点只实现每请求追踪与限步，不新增幂等存储、会话系统或防重 TODO；后续危险写操作 / 命令执行时再把幂等作为独立工程要求处理。

### `A4-Gate-C4a-1e`｜首次模型调用的占步、计时与日志接线

- 新工具 `perf_counter()`：Python 标准库提供的单调高精度间隔计时器，适合测量一段操作耗时，不受系统时钟调校影响；两次读数相减得到秒，乘 `1000` 并转成非负整数即合同要求的 `duration_ms`。
