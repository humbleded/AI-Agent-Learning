### 最大步数片段｜先拦住下一次工具执行，再用框架上限兜底

本地 `document_analysis_agent.mdx` 展示了 `assistant → tools → assistant` 回环，却没有给这个回环加入任务所需的明确业务预算。当前项目不能只照搬回环；必须回答“已经用完诊断次数时，下一次工具到底会不会被执行”。

#### 1. 先冻结 `step_count` 的含义

在当前工具分支中，`step_count` 表示**已经处理过多少次诊断工具请求**。未批准请求和执行失败也会占用一次预算，因为系统已经为这次请求做了授权判断或执行尝试；它不是“成功获得证据的次数”。

```text
step_count = 已处理请求数
max_steps  = 最多允许处理的请求数
```

计数含义必须固定，否则一个 Node 把它当“工具次数”，另一个 Node 把它当“全部 Graph 节点数”，停止条件就无法预测或测试。

#### 2. 在进入工具 Node 之前检查边界

已经通过的条件路由包含：

```python
if state["step_count"] >= state["max_steps"]:
    return "max_steps_stop"
```

它位于 `review_evidence` 之后、`run_readonly_diagnostic` 之前。这样，当当前计数已经达到上限时，Graph 直接进入停止 Node，外部工具不会再执行。

```text
review_evidence
      │
      ▼
route_after_review
      ├─ step_count >= max_steps
      │        → max_steps_stop → END
      │
      └─ 仍有预算
               → run_readonly_diagnostic
                    └─ 真正处理一次请求，并把 step_count + 1
```

如果把检查放在工具调用之后，系统会先产生一次真实调用、费用、延迟或外部读取，再说“已经超限”。这叫“发现得太晚”：即使最后的 State 写了停止原因，也无法撤销刚才已经发生的工具调用。

#### 3. 等于边界时停止，差一步时允许最后一次

- `step_count == max_steps`：预算已经用完，不得再进入工具 Node。
- `step_count < max_steps`：仍可处理一次请求；工具 Node 处理后把计数加 1。
- 使用 `>=` 而不是 `==`：即使脏数据或旧 bug 已经让计数越界，仍然会停止，不会因为错过“恰好相等”的瞬间继续循环。

例如 `step_count=1, max_steps=2` 时还允许最后一次请求；工具处理后计数变成 2。随后若证据仍未知，再次经过路由时就进入 `max_steps_stop`。

#### 4. `recursion_limit` 是框架保险丝，不是业务停止规则

`recursion_limit` 限制的是一次 Graph 运行最多经历多少个 `super-step`。这里的 `super-step` 可以先理解为 Graph 的一轮节点调度：顺序执行的 `review_evidence` 和 `run_readonly_diagnostic` 属于不同步骤，因此它并不等于“工具调用次数”。

```text
业务 max_steps
  → 计算诊断请求预算
  → 路由到 max_steps_stop
  → 可以得到明确 stop_reason

框架 recursion_limit
  → 计算 Graph super-step
  → 防止接错边或终止条件失效造成无限循环
  → 超限通常抛出 GraphRecursionError
```

所以正式实现会保留两层保护：用 `max_steps` 正常、可解释地结束业务流程；再配置 `recursion_limit` 捕获图结构或路由失效。不能只提高 `recursion_limit` 来“修复”无限循环，也不能把它当成精确的工具预算。

### 测试片段｜分别证明 Node、路由、整条 Graph 和副作用边界

`compile()` 成功只说明 Graph 的基础结构可以编译。它不会替我们证明 Node 返回了正确字段、条件路由选对了分支，也不会证明达到上限时外部工具没有被多调用一次。要让失败容易定位，需要按“被测范围”分层。

```text
范围最小、定位最快                         范围最大、最接近真实流程

Node 单测 ──→ route 单测 ──→ 整条 Graph 测试 ──→ 真实 DeepSeek 集成验证
   │              │                 │
精确局部更新     下一节点名       连线、合并、循环、停止
                                  ＋ spy 观察调用次数
```

#### 1. Node 单测：只问“这个 Node 返回什么局部更新”

Node 本质上仍是接收 State、返回 State 局部更新的 Python 函数。最小测试可以直接调用这个函数；当前官方文档也说明，编译后的 Graph 可用下面的方式单独执行已注册 Node：

```python
update = compiled_graph.nodes["review_evidence"].invoke(state)

assert update == {"evidence_status": "insufficient"}
```

这一层适合检查：读了哪些字段、返回了哪些字段、错误码是否稳定、`step_count` 是否只加一次、没有 reducer 的 `evidence` 是否保留了旧值。它不执行整条 Graph，因此不能证明边接对了或下一站选对了。

#### 2. route 单测：只问“给定这份 State，下一站是谁”

`route_after_review` 是普通 Python 路由函数，可以直接传入固定 State：

```python
next_node = route_after_review(state)

assert next_node == "max_steps_stop"
```

测试时要分别覆盖工具失败、达到最大步数、证据不足、证据充足和继续诊断等输入。它能精确证明路由优先级和目标节点名，却不会执行 Node、工具或整条 Graph。

#### 3. 整条 Graph 测试：问“节点和边连起来后，流程真的这样走吗”

这一层从 `initial_state` 调用 `compiled_graph.invoke()` 或观察 `stream(..., stream_mode="updates")`，检查：

- 最终 State 是否正确；
- 实际出现的 Node 更新顺序是否符合预期；
- 工具执行后是否真的回到 `review_evidence`；
- 循环是否在正确边界停止。

测试里使用返回固定结果的假模型或假工具，使相同输入每次都走相同路线。这样才能稳定复现成功、失败和超限场景。真实 DeepSeek 调用仍需单独做集成验证；它证明真实连接和模型链路可用，但不能代替这些可重复的故障测试。

#### 4. spy：不只看结果，还记录“工具入口实际被调用了几次”

spy 可以先理解成“会记账的假工具”：它不访问真实外部服务，但每次被程序调用都会把自己的 `call_count` 加 1。它不是另一种 Graph，而是测试中用来观察副作用边界的替身。

在 `step_count == max_steps` 的整图测试里，至少要同时断言：

```python
assert result["stop_reason"] == "max_steps_reached"
assert diagnostic_spy.call_count == 0
```

只断言第一行不够。一个有 bug 的 Graph 完全可能先多调用一次工具，随后再进入 `max_steps_stop`，最后仍得到正确的 `stop_reason`。最终 State 只能说明“最后写成了什么”，spy 才能说明“途中有没有发生本不该发生的外部调用”。

本片段不引入 checkpointer、`thread_id`、持久化、恢复或中断；这些属于后续 persistence / interrupt 任务，不是 `G8-00` 当前测试范围。

### 带读收尾｜要点与定义清单

📌 核心定义：

- **State**：Graph 各步骤共享的数据；`TypedDict` 主要提供静态类型提示，不会替普通 Python 字典完成完整运行时校验。
- **Node**：读取 State、完成一个职责并返回局部更新的执行步骤；未修改字段不必重复返回。
- **Edge / conditional edge**：规定 Node 的固定下一站，或根据当前 State 选择唯一业务分支；路由函数负责选择，不负责冒充业务 Node 更新 State。
- **StateGraph / compiled graph**：`StateGraph` builder 负责声明结构，`compile()` 生成可 `invoke()` / `stream()` 的可执行 Graph；重新修改 builder 后需要重新编译。
- **Reducer**：决定同一 State 字段如何合并更新；未配置 reducer 时默认替换，因此 `evidence` 要保留旧值时由 Node 自己构造完整新列表。
- **State streaming**：`stream_mode="updates"` 输出各 Node 的局部更新，`stream_mode="values"` 输出完整 State 快照，`stream_mode="messages"` 用于模型消息 token；每次 `stream()` 都是一次新运行，不是回放旧 `invoke()`。
- **业务预算与框架保险丝**：`max_steps` 统计已处理的诊断请求并正常路由到 `max_steps_stop`；`recursion_limit` 统计 Graph `super-step`，超限抛出 `GraphRecursionError`。
- **spy**：会记录调用次数和参数的可控替身；用于证明工具入口有没有被调用，补足最终 State 看不到中途副作用的缺口。

🔑 关键要点：

- 多样日志可交给 LLM 理解和归纳，但“继续、证据不足停止、工具失败停止、最大步数停止”由应用代码确定。
- `bind_tools` 让模型能够生成结构化工具请求，不等于工具已经执行；应用代码仍负责 allowlist、参数、执行异常、业务 State 写回和停止规则。
- 达到 `max_steps` 时必须在进入外部工具 Node 之前停止；差一步时只允许最后一次请求，再回到 `review_evidence` 重新判断。
- 测试从小到大分别保护 Node 局部更新、route 返回值、整图连线与状态合并；涉及工具次数时必须增加 spy 断言。
- 改大小写、检查 JSON 是否缺字段等无需持续 State、分支循环和恢复的简单任务，普通 Python 函数或循环更合适，不必为了使用框架而引入 LangGraph。

⚠️ 易混点：

- `updates` chunk 不是完整 State；`values` 才是完整快照。
- `START`、`END` 是入口/终止标记，不是返回 State 更新的业务 Node。
- `max_steps_stop` 不设置最大次数，只在路由已判定达到上限后写入稳定 `stop_reason`。
- `recursion_limit` 不等于工具调用数，也不应作为正常业务停止结果。
- 最终 `stop_reason` 正确不能证明途中没有多调用工具；必须检查 spy 调用次数或等价的副作用证据。
