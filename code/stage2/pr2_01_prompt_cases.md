# PR2-01 Prompt 基础 · 三个 prompt 对比

> 任务（阶段 2 PR2-01 动手交付）：对**同一个抽取任务**，写 3 个"讲究程度"递进的 prompt，真实调 DeepSeek 对比效果、得结论。
> 驱动脚本：`code/stage2/pr2_01_run_cases.py`（原样发送下面三个 prompt，并对每段输出自动做 `json.loads` 检测）。
> 运行：`.venv/Scripts/python.exe code/stage2/pr2_01_run_cases.py`
> 模型：`deepseek-v4-pro`（reasoning 模式）。日期：2026-06-27。

## 任务

从同一段中文自我介绍里，抽取 6 个字段（`姓名/年龄/公司/城市/职位/邮箱`）成 JSON。
3 个 prompt 喂的是**同一段输入**，只改 prompt 的"讲究程度"，看输出差异（这是"同一任务对比"的前提）。

固定输入文本：

> 大家好，我叫李雷，今年 28 岁，目前在北京的字节跳动担任后端工程师，主要用 Go 语言，联系邮箱是 lilei@example.com。

---

## 三个 prompt + 真实输出

### prompt① 偷懒模糊版（zero-shot：不点字段、不要格式）

```text
抽取下面文本的信息，"""大家好，我叫李雷，今年 28 岁，目前在北京的字节跳动担任后端工程师，主要用 Go 语言，联系邮箱是 lilei@example.com。"""
```

真实输出：

```text
从文本中提取到的信息如下：

- 姓名：李雷
- 年龄：28 岁
- 所在地：北京
- 公司：字节跳动
- 职位：后端工程师
- 主要编程语言：Go
- 联系邮箱：lilei@example.com
```

`json.loads`：✗ **失败**（不是 JSON，是 Markdown 列表 + 开场白）

### prompt② 清晰具体版（角色 + 分隔符 + 点名 6 字段 + 空 JSON 模板 + 前后不带文字）

```text
你是一个信息抽取助手，需要你抽取用"""标记的文本，抽取其中的姓名,年龄,公司,城市,职位,邮箱。并且必须按照以下JSON的格式输出，{"name":"","age":"","company":"","city":"","position":"","email":""}，JSON前后不能带有文字。
"""
大家好，我叫李雷，今年 28 岁，目前在北京的字节跳动担任后端工程师，主要用 Go 语言，联系邮箱是 lilei@example.com。
"""
```

真实输出：

```json
{"name":"李雷","age":"28","company":"字节跳动","city":"北京","position":"后端工程师","email":"lilei@example.com"}
```

`json.loads`：✓ **成功**（纯 JSON，6 字段齐，前后无文字）

### prompt③ few-shot 加强版（② 的全部 + 一组填好的"张三"样例）

```text
你是一个信息抽取助手，需要你抽取用"""标记的文本，抽取其中的姓名,年龄,公司,城市,职位,邮箱。并且必须按照以下JSON的格式输出，{"name":"","age":"","company":"","city":"","position":"","email":""}，JSON前后不能带有文字。
示例:
输入:大家好，我叫张三，今年 20岁，目前在深圳的腾讯担任前端工程师，主要用 Go 语言，联系邮箱是 zhangsan@example.com。
输出:{"name":"张三","age":"20","company":"腾讯","city":"深圳","position":"前端工程师","email":"zhangsan@example.com"}

"""
大家好，我叫李雷，今年 28 岁，目前在北京的字节跳动担任后端工程师，主要用 Go 语言，联系邮箱是 lilei@example.com。
"""
```

真实输出：

```json
{"name":"李雷","age":"28","company":"字节跳动","city":"北京","position":"后端工程师","email":"lilei@example.com"}
```

`json.loads`：✓ **成功**（与 ② 输出**完全一致**）

## 对比表

| 维度 | ① 偷懒模糊 | ② 清晰具体 | ③ few-shot |
| --- | --- | --- | --- |
| 能否 `json.loads` | ✗ 失败 | ✓ 成功 | ✓ 成功 |
| 输出形态 | Markdown 列表 + 开场白 | 纯 JSON | 纯 JSON |
| 字段是否可控 | 否（多抽"编程语言"、城市写成"所在地"、key 是中文） | 是（6 字段、英文 key 锁死） | 是 |
| 值是否干净 | 否（"28 岁"带单位） | 是（"28"） | 是 |
| 程序能否直接用 | 否（要正则/字符串硬切，又脏又脆） | 是 | 是 |
| prompt 长度/成本 | 最短 | 中 | 最长（多一整段示例 token） |
| 相对 ② 的增益 | —— | 基准 | **0**（输出一样，纯多花 token） |

---

## 结论

1. **清晰具体 >> 偷懒**：① 因为没点字段、没要 JSON，模型只能"自由发挥"成 Markdown 列表，还多抽字段、值带单位、key 不可控，程序根本拿不动；② 把"要哪 6 个字段 + 输出纯 JSON + 前后不带文字"全说死，输出直接 `json.loads` 进字典。**好 prompt 值钱在"消除模型的自由发挥空间"。**
2. **few-shot 不是越多越好**：在这个规整、边界清晰的任务上，③ 的 few-shot 和 ② 输出完全一样、**零增益**，却白白多花一整段示例的 token + 延迟。
3. **prompt 不是越长越好**：长 ≠ 好，**清晰描述 + 给思考时间**才好。few-shot 只在"任务边界模糊 / ② 还压不稳格式"时才值得加（帮模型划边界、锁格式）；需求与边界都清晰时，加 few-shot 是纯成本浪费，塞太多无关示例还会稀释核心指令。**加不加 few-shot，看任务难度，是个工程判断。**

> 延伸（今天没做，留作下次）：想让 ③ 的 few-shot"扳回一城"，得换个 ② 会栽的**难输入**（字段缺失 / 顺序打乱 / 表述刁钻），并在示例里演示"缺字段填 `null`"，才看得出 few-shot 的价值。

## 三个必答

1. **好 prompt 通常包含哪些要素？**
   清晰具体的指令（说清做什么、要哪些字段）+ 指定输出格式（锁 JSON、给空模板、要求前后不带文字）+ 必要时给角色定风格 + 用分隔符把数据和指令分开 + 复杂题加 few-shot/CoT 给思考时间。核心是**不给模型自由发挥的空间**。

2. **示例 few-shot 解决什么问题？**
   用"做好的样例"代替大段文字解释，帮模型摸清任务的**边界和细微差别**、锁定**输出格式/风格**（照葫芦画瓢）。注意 **few-shot 真实示例 ≠ schema 空模板**：② 给的是 schema（结构骨架），③ 给的才是 few-shot（填好的真实样例）。前提是任务真需要——边界清晰的简单任务，few-shot 收益 ≈ 0。

3. **什么时候 prompt 越长反而越差？**
   当多出来的内容是**无关 / 冗余**示例时：① 多花 token、增加延迟；② 还可能稀释核心指令、让关键信息被淹没。本次实锤——③ 比 ② 长一整段示例，输出却一模一样，纯亏成本。**长 ≠ 好，相关 + 清晰才好。**
