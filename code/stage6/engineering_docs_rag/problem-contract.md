只读范围固定为 `D:/AI-Knowledge/02-Concepts`、`03-Courses`、`05-Papers` 的 Markdown；排除 README/index.md 等指定索引、规则文件、隐藏项、符号链接和 Windows reparse/junction，按文件和总量限制读取，不跟随 wiki 链接扩展范围。`08-Memory`、copilot、raw、任意其他个人目录和真实公司资料不在范围。最初只读盘点为 89 个 Markdown，包含索引；2026-09-08 实际运行筛选出 79 份文件、切成 450 个片段，这是当次快照，当前允许文件数由状态接口计算，不能把 89 当作有效语料数。课程目录含计划与进度，引用它们不能作为学习掌握证据；最初 `05-Papers` 只有 README，不能据此声称有论文正文。

实现流程：现成 LangChain `TextLoader` 读取 → `MarkdownTextSplitter` 切分 → `BM25Retriever` 建本次内存文本索引 → `ChatOpenAI` 调用已配置的真实 DeepSeek，由显式 LangGraph 连接模型选择搜索、执行搜索、片段回填与回答。模型至少检索一次，每次问答最多 2 次搜索、每次最多 4 片段；引用限定为本次返回的资料编号。模型一次返回多个工具调用时，先校验整个批次的参数与剩余预算，再串行执行，每个调用各占一次搜索预算。BM25 是按词语匹配排序的检索，不能冒充 embedding/pgvector 已完成。当前 community 组件使用固定版本，扩大格式或准备部署时继续按维护状态重新核验和迁移。

本轮实际联调中，DeepSeek 自主生成两组搜索词并执行两次检索，最终给出 6 条引用，对应原文已成功打开；也验证了模型在 `parallel_tool_calls=False` 时仍可能一次返回两个工具调用，因此修复为上述整批校验后串行执行，不能依赖模型必定一次只调用一个工具，也不能一律拒绝合法多调用。当前 API 测试结果为 42 passed，详细执行证据由主实施者记录在同日 daily；这些是助手工程实现的验证，不是学生课程 PASS。

数据边界：向 DeepSeek 发送用户问题与有限命中片段，不上传整库或个人 Memory；文件内容按资料处理，不执行文档命令。原知识库保持只读，索引在本地内存中按查询重建，不把缓存、问答或样式选择写回知识库。原文通过服务端生成的 `source_id` 查看，浏览器不能指定任意文件路径；资料不足或引用不满足要求时不展示编造的可靠结论。引用编号校验只检查出处范围，完整答案质量与权限评估仍待课程相应检查点覆盖。

## 已授权的后续扩展：四类记忆、图片与音频

2026-09-08 用户明确要求：“我想把图片、音频记忆和教材那套完整四类架构也加入到项目中”。据此把 `D7-03` 的实现目标固定为本工程文档助手；下面是助手整理的后续设计，功能尚未实现，也不计用户学习证据。当前 `R6-01` 的五个目标继续有效，新增范围在 D7-03 分段学习与验收。

扩展场景：开发人员除了查询项目文档，还能经明确授权保存项目交接、排错经过、截图与语音说明，之后跨会话找回可核对的经验。文档知识库与个人/团队经验分别记录来源、适用版本和访问范围；记忆内容不能自行覆盖官方文档或扩大访问权限。

| 记忆类型 | 在本项目中解决什么问题 | 必须看到的行为 |
| --- | --- | --- |
| 工作记忆（WorkingMemory） | 跟住这次对话正在讨论的服务、版本和排错步骤 | 多轮追问能承接当前上下文；有容量、输入长度和过期限制，不自动变成永久事实 |
| 情景记忆（EpisodicMemory） | 找回“什么时候发生了什么、当时怎样处理、结果怎样” | 按用户/团队、项目、时间与事件检索交接或排错记录；能跨会话恢复事件及关联证据 |
| 语义记忆（SemanticMemory） | 记住已确认且可复用的项目事实、偏好和关系 | 带出处、版本与有效期保存事实，支持更新和冲突处理；用最小实体/关系例子查询“服务依赖什么”，未经确认的推断只作候选 |
| 感知记忆（PerceptualMemory） | 找回看过的截图、听过的交接录音 | 保存原图、原音频及其关联记录，既能用文字找图片/音频，也能用图片找相似图片、用音频找相似音频；结果能定位到原图或录音片段 |

四类记忆共用管理入口、统一记录和配置、存储接口及编码接口，分别实现各自的写入、检索和保留规则；这是职责划分，不要求四个 Agent、四个数据库或四个服务。参考教材的分层思路，把管理层、四类实现、存储层与编码层接起来；存储沿用 PostgreSQL/pgvector，实体与关系先用关系表表达，媒体原件通过可替换的文件/对象存储接口保存。数据库是长期记录及媒体关联的事实源；Redis 若使用，只作缓存。

框架连接：记忆检索注入、候选整理、确认与遗忘，以及图片/音频处理，逐步接入本项目已有 LangGraph 工作流。优先复用 LangChain 的模型/工具/检索集成与 LangGraph 的状态/存储能力；框架未提供的四类业务规则、媒体处理或生命周期只补必要适配，不建设平行编排，也不声称框架自动实现了全部四类记忆。

图片从截图中的文字提取与内容描述入手，再接真实图像编码和检索；音频从带时间位置的转写入手，再接真实音频编码和检索。提取文字、转写和文件路径都是辅助信息，不能代替最终的图片/音频记忆。每条衍生记录关联原件、所属用户/团队、模型版本与位置；不同模型或维度的向量分开管理。文字找图或音频时，要用与目标媒体对齐的编码器或经过验证的转换链路，不能直接比较互不兼容的向量，也不要求图像与音频直接互搜。

学习与实现按 D7-03 内部六个检查点推进，允许跨多个 Session：

1. 讲清四类职责、记忆与 RAG/执行恢复的区别，接通统一管理入口和有边界的工作记忆。
2. 实现跨会话情景记录、已确认事实及最小实体/关系查询，保留来源和冲突处理。
3. 加入真实图片的保存、编码、文字找图与相似图片检索，回答能指向原图。
4. 加入真实音频的保存、带时间位置的转写、编码、文字找音频与相似音频检索，回答能定位片段。
5. 串起“写入 → 找回 → 整理成候选 → 确认/更新 → 过期或删除”；整理不等于自动确认事实。删除和过期后，原件、衍生文本、向量、缓存与关联引用按所有权及保留规则联动失效，不影响其他用户仍合法持有的资料。
6. 完成访问隔离、恶意记忆、媒体处理失败与恢复回归，并比较无记忆、仅文本记忆、完整四类记忆的实际收益与代价。

未来成功例（教学设定，尚未执行）：用户保存一次虚构工单服务启动失败事件，关联报错截图和一段交接录音。第二次会话问“上次启动失败怎么解决，依据在哪里”，助手找到那次事件、适用版本的已确认事实、原图和录音时间段，结合可访问的文档回答；本轮再问“那张截图呢”时，工作记忆能承接。删除该事件及其独占附件后，后续检索不再返回这些记录或衍生内容；另一用户不能通过检索或媒体链接访问它们。
